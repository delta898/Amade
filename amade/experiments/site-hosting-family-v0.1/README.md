# Amade Site Hosting Template Family 0.1.0 proof

규범 draft는 [`amade/spec/site-hosting-family-v0.1-draft.md`](../../spec/site-hosting-family-v0.1-draft.md)에 있습니다. 구형 1.x 형식은 [`amade/spec/README.md`](../../spec/README.md)에 legacy reference로 정리되어 있으며, 이 실험은 그 스키마를 사용하거나 대체하지 않습니다.

Experimental proof source for the Amade `dev` catalog. The canonical manifests/packages now live under `amade/families/`, `amade/templates/`, and `amade/catalog/index.json`; this folder retains the isolated build/verification fixtures. `catalog.json` remains a local proof index. Family and template names/details stay in their manifests; consumers pin references to one Amade revision and verify IDs and `family_id` links.

A materialized Site has sibling `site-data/` (durable family data) and `template/astro/` (replaceable presentation source). `family.json` declares `site_data_directory: "data"`, the initial family seed copied into the Site's `site-data/`; each template's `astro_project` points to its package-relative Astro project (`astro/`). Template code references only `site-data/`, never an Amade repository path. Site identity, logo, and editable menu items live in `site-data/site.json`; family Markdown entries live under `site-data/data/`. Switching templates replaces `template/astro/` while retaining `site-data/`.

The personal family compares a post list with a card grid. The company family compares service cards with a left-side navigation/list composition. Fixtures include public/private Markdown, authored pages, the site logo, and entry-relative SVG media. Template manifests carry common metadata (`name`, `description`, `author`, package `version`, `license`, `categories`, `tags`, and a representative `preview`) plus optional `screenshots`, `homepage`, and `support`. Every template declares `status`: `active` is offered for new Sites, `deprecated` is hidden from new-Site choices while retained for existing Sites, and `withdrawn` is neither offered nor downloadable for new Sites. BlogGenius filters new choices to `active` and keeps locally materialized existing Sites buildable. Categories and tags aid discovery but do not define family compatibility.

Each template uses Astro/Zod schemas to validate its `site.json` and family-specific Markdown frontmatter. Content IDs are lowercase ASCII kebab-case and loaders enforce that the file path and frontmatter `kind` agree. Personal templates accept pages, posts, and work items; company templates accept pages, posts, and services. Both schemas reject unknown fields, require post dates and descriptions, and default missing `is_public` to private. The loaders read content from `site-data/data/`; authored page paths may be nested (the proof covers `/about/team/`).

Run `python3 scripts/build_and_verify.py /private/tmp/amade-site-hosting-v01-proof`. It materializes both Sites, performs A→B→A builds per family, verifies catalog references, the same editable navigation, all routes and media, and confirms family data hashes are unchanged. Output goes to a new directory; the script refuses to overwrite an existing one. Scratch negative builds have also confirmed rejection of non-canonical IDs, mismatched path/kind, and unknown frontmatter; repeatable negative fixture coverage is still pending. This experimental catalog is not consumed by BlogGenius.
